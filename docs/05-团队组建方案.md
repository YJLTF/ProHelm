# ProHelm（项舵）团队组建方案

> 版本：v0.1｜日期：2026-11-14｜配套：《04-开发计划》
> 前提：M1 为 3 个月、6 个 Sprint 的攻坚期；团队规模按"最小可执行"原则设计。

---

## 1. 角色矩阵（M1 所需的全部职能）

| 职能 | 职责 | 人力方案 A（标准） | 人力方案 B（极简） |
|---|---|---|---|
| 产品/项目管理 | 需求决策、Sprint 计划、内测用户运营 | 创始人 | 创始人 |
| **Rust 核心工程师** | helm-core：DB/算法（CPM/EVM）/AI 网关/后续同步 | **专职 1 人** | 创始人 + AI，外聘顾问 review |
| **TS/前端工程师** | React UI、甘特图、看板、AI 交互层 | **专职 1 人**（可与上互备） | 创始人 + AI |
| DevOps/发布 | CI、三平台打包、签名、更新链路 | 两人分担 | 创始人 + AI |
| 内容设计 | PMP 知识库撰写、30+ 工件模板、UI 文案 | 两人分担 | 创始人 + AI（人工校验） |
| 视觉设计 | 品牌与界面视觉 | 外包/模板（S3 前） | 模板 + AI |
| 测试 | 冒烟清单、黄金用例、内测反馈分类 | 两人分担 + AI 生成用例 | AI 生成 + 创始人执行 |

**关键洞察**：AI 智能体（ZCode 等）可承担约 **60~70% 的编码量**（CRUD、UI、配置、测试生成、文档），但三类工作必须由人兜底：**算法正确性（CPM/EVM/同步合并）、安全设计（加密/密钥）、产品验收（交互手感与方法论准确性）**。

## 2. 两个配置方案

### 方案 A · 标准（推荐预算允许时）：2 人力 + AI 梯队

```
创始人 ── 产品/项目/内容 + TS 互备
Rust 工程师 ── helm-core + AI 网关 + 打包
AI 智能体（ZCode）── 编码副驾 / 测试生成 / 文档 / Code Review 初筛
```

- 成本：约 2 份薪资（或 1 份薪资 + 1 名合伙人）+ AI 订阅
- 产能：可支撑《04-开发计划》的 6 Sprint 排期，有余量
- 招聘顺序：**Rust 工程师最先**（核心层是瓶颈）

### 方案 B · 极简（创始人单人 + AI）：可行，但有明确边界

- 创始人需具备基础工程能力，AI 承担主要编码
- **风险兜底**：S2 开始前找到一名 Rust 顾问（按次付费 review CPM/EVM 关键代码，约 5~10 次/月）；S4 AI 网关与 S3 模板同理
- 产能现实：Sprint 交付率预期下调至 60%，M1 可能延后 2~4 周 —— 需在 S3 结束时复盘决定是否转方案 A
- 适合：验证期快速试错；不适合：直接冲公测

**建议**：起步用 B（本会话已完成 S1 骨架），S2 结束（12/11）评估：若 CPM/甘特质量或进度不达预期，立即转 A 招 Rust 工程师。

## 3. AI 智能体工作流（本次已实践并固化的模式）

```
任务卡（04 文档 backlog ID）
   → 指派 AI 实现（分支上工作，产出代码+测试）
   → 人工 Review（算法正确性 / 安全 / 交互验收 三道门）
   → 本地验证（CI 同款命令）
   → 合并 main，更新 backlog 状态
```

规则：

1. **AI 不直接动 `main`**：一律走分支 + 人工合并
2. **AI 产出必须带测试**：无测试的 PR 不进入 review
3. **三道人工 review 门**：算法、安全、UI 验收（哪怕 AI 全自动生成）
4. **上下文供给**：每个任务卡给 AI 附上对应设计文档章节（01~05），避免 AI 凭空发明需求
5. **Review 反馈回灌**：review 意见沉淀到 `docs/conventions.md`，AI 后续生成质量随项目知识库提升

## 4. 协作节奏（Sprint 机制）

| 仪式 | 频率 | 时长 | 产出 |
|---|---|---|---|
| Sprint 计划会 | 每周一 | 30 min | 本 Sprint P0 清单确认 |
| 每日站会 | 每日 | 15 min | 昨天/今天/阻塞（单人时=自我站会+AI 任务日志回顾） |
| Demo + 复盘 | 每周五 | 45 min | 可运行 demo + 一条改进项落入下 Sprint |
| Sprint 回顾调整 | 每 2 周 | — | 交付率复盘，团队方案 A/B 切换检查点（S2、S4 各一次） |

工具链：GitHub（仓库/PR/Actions）+ GitHub Projects（backlog 看板）+ ZCode（编码副驾）。**内测起用 ProHelm 自身管理本项目（dogfooding）**——吃自己的狗粮是最快的产品反馈来源。

## 5. 招聘要点（按需启用）

### Rust 核心工程师（最先招聘 / 或顾问）

- 必备：Rust 生产经验 ≥1 年；熟悉 rusqlite/SQLite；能独立设计模块 API
- 加分：Tauri/桌面端经验；桌面软件发布经验；对项目管理领域有兴趣
- 考察方式：现场实现"内存 SQLite 上跑迁移 + 事务性 upsert"小题 + 评审一段现有 helm-core 代码
- 顾问模式：按次 review（CPM/EVM/同步合并/加密四个关键模块各 2~3 次），费用约为全职的 5~10%

### TS/前端工程师（方案 B 转方案 A 时招）

- 必备：React 19 + TS 严格模式实战；复杂状态/表格/拖拽交互经验
- 加分：ECharts/甘特图组件经验；Tauri/Electron 项目经验；审美在线（能直接落实 UI）

### 视觉设计（外包即可）

- S3 前完成：Logo/图标体系、浅色主题设计 token、品牌物料（官网落地页素材）
- 预算：外包 1~2 周，风格要求见《02-功能设计》命名隐喻章节（克制、专业、航海隐喻点到为止）

## 6. Onboarding Checklist（新成员/新 AI 会话通用）

1. 读 `README.md` → `docs/01~05`（按序）
2. 跑通开发环境：`pnpm install && pnpm build && cargo test -p helm-core`（见 README 开发指南）
3. 跑通一次完整流程：改一行 UI 文案 → 本地构建 → 造一个小 PR
4. 阅读 `docs/conventions.md`（S1 收尾时创建：命名、错误处理、文案规范）
5. 领第一个 `P1` 级任务卡走完整工作流（含 AI 实现 + 人工 review）

---

## 7. 决策机制

- **日常决策**：Sprint 内技术选型小分歧 → 实现者定，demo 时公开
- **架构决策**（ADR）：影响数据模型/外部接口/依赖引入的决策写一条轻量 ADR 到 `docs/adr/`（格式：背景/决策/后果，半页以内）
- **切换检查点**：S2 结束与 S4 结束各做一次方案 A/B 评估，依据：交付率、代码质量抽查、创始人带宽
- **止损线**：连续 2 个 Sprint 交付率 <50% 或核心质量门连续失守 → 立即转方案 A 并调整范围（先保甘特图+AI 问答两块招牌功能）
